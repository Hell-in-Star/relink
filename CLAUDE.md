# CLAUDE.md — проєкт ReLink

## Що це за проєкт

Репозиторій рекрутингової агенції ReLink (Defense / MilTech / виробництво).
Тут живуть: брендбук, LinkedIn-стратегія, вихідні матеріали бренду і робочі документи.

## Структура тек

- `/context` — текстові файли знань (брендгайд, палітра, тон, структура послуг).
  Ця тека синхронізується у knowledge браузерного проєкту Claude — тримати її чистою і актуальною.
- `/assets/source` — вихідники лого й макетів (SVG, PNG високої роздільності).
  Лого: `/assets/source/лого/svg/` і `/assets/source/лого/png/`. Деталі, які файл для
  якого фону: `/context/логотип.md`.
- `/assets/reference` — референси стилю і структури (експорти з Figma: PDF, PNG, текстові описи).
  Для задач типу «зроби як це, але за нашим брендом». НЕ джерело правди — правда в `/context`.
- `/assets` — ZIP-архіви для завантаження.
- `/docs` — робочі документи (стратегія, КП тощо). `docs/план.md` — трекер проєкту.
- `/smm` — дослідження і стратегія присутності в соцмережах (LinkedIn,
  Facebook, Instagram, Threads). Загальний файл описує тільки спільне,
  мережевий — тільки відмінності; вміст не дублюється. Карта теки —
  `smm/README.md`, короткий покажчик для браузерного Клода — `/context/smm.md`.
  LinkedIn: дослідження готове, стратегія затверджена (джерело правди —
  `relink-linkedin-strategy.html` у корені). Facebook/Instagram/Threads —
  не розпочато.
- `/presentation` — презентація компанії: `relink-presentation.html` (затверджена,
  джерело правди), `relink-presentation.pdf` (9 сторінок, друкований вигляд),
  `relink-presentation.pptx` (9 слайдів, редагований — картинкою лише фони,
  складна графіка слайда 1 і логотипи/іконки, решта редаговані фігури й текст).
  Перезбірка: `build-pdf.js` (Playwright) і `build-pptx.py` (python-pptx, читає
  активи з `pptx-assets/`, згенеровані `pptx-assets/render-assets.js`).
  `pdf-preview/` і `pptx-preview/` — контрольні PNG-рендери сторінок/слайдів
  для звірки (оновлюються при кожній перезбірці, не джерело правди). Деталі
  архітектури й відомі обмеження — `presentation/pptx-звіт.md`. Короткий опис
  структури й дизайн-рішень самої презентації — `/context/презентація.md`.
- `/archive` — застарілі файли. Нічого не видаляємо — тільки архівуємо.

## Перезбірка PDF/PPTX презентації після правок HTML

`relink-presentation.html` — джерело правди; PDF і PPTX з нього НЕ генеруються
автоматично, перезбирати вручну після кожної затвердженої правки HTML:

```
cd presentation
npm install                       # один раз (Playwright для build-pdf.js)
node build-pdf.js                 # -> relink-presentation.pdf
node pptx-assets/render-assets.js # перегенерувати активи (фони/графіку/іконки)
python build-pptx.py              # -> relink-presentation.pptx (потрібен python-pptx, Pillow)
```

Потрібні системні інструменти (встановлюються один раз): Node.js, Python 3,
`pip install python-pptx pillow`. Для перевірки якості рендеру (не обов'язково
для щоденної роботи): Poppler (`pdffonts`/`pdftoppm`) і LibreOffice (headless
рендер pptx→png для звірки з HTML-версією).

**Якщо PDF зібрався «з полями»** (вміст сторінки менший за саму сторінку,
порожні смуги праворуч/знизу) — це НЕ розмір сторінки (той лишається
правильним, 960×540pt), а баг рендер-пайплайна Chromium/Skia на цій
машині: масштабування екрана Windows (де саме — до кінця не з'ясовано,
DPI-перевірки показують суперечливі значення) просочується у друкований
рендер і стискає вміст сторінки на постійний коефіцієнт. Фікс уже в
`build-pdf.js` — параметр `scale: 1.5` у виклику `page.pdf()`, компенсує
баг множенням. Якщо після якогось оновлення Playwright/Chromium баг
повернеться в іншому вигляді (інший коефіцієнт) — шукати новий коефіцієнт
через `pdfinfo`/побіксельну перевірку кутів рендеру, не змінювати HTML.

**Шрифти в PPTX не вбудовуються автоматично** — `python-pptx` не має
API для цього. У файлі прописані правильні НАЗВИ шрифтів (Geologica
Medium/Regular, Onest Light/Regular/Medium), але щоб текст показувався
саме ними (а не системним замінником), треба або встановити ці TTF з
`assets/source/шрифти/` на машині, де відкривають файл, або вручну
ввімкнути вбудовування шрифтів у самому PowerPoint після відкриття
(Файл → Параметри → Збереження → «Вбудовувати шрифти у файл»)
і зберегти файл ще раз.

## Бренд (коротко)

- Палітра v4.0 — основа стилю тепер **градієнти** (замовнику не подобаються чисті кольори без градієнта):
  бурштин `#DEA102`→`#ECC668`, графіт `#394050`→`#C6D7FF`, сірий `#707787`→`#E0EAFF`, білий `#EBEAE8`→`#767676`.
  Великі поверхні — градієнт, дрібні елементи (текст, лінії) — чистий колір. Іконки — окремо під кожен макет.
  Деталі й точні координати градієнтів: `/context/палітра.md`.
- Шрифти: Geologica (заголовки, Medium; іноді Regular) + Onest (текст,
  Light/Regular/Medium). Деталі, зокрема виправлення побитих метаданих TTF —
  `/context/типографіка.md`.
- Логотип: горизонтальний лендмарк (іконка + напис), вихідники в `/assets/source/лого/`.
  Деталі, які файл для якого фону, і застереження про HEX: `/context/логотип.md`.
- Застаріла айдентика (не використовувати): жовтий `#F5C800`, темно-синій `#0B1724`, шрифти Fixel Display / Inter / Oswald.

## Джерело правди

- Усе в цьому файлі — знімок на момент останнього оновлення. Змінюватись може
  будь-що: палітра, шрифти, структура тек, перелік актуальних файлів, стратегія.
- Актуальний стан проєкту — це файли в `/context` і сам репозиторій.

- Якщо CLAUDE.md суперечить вмісту репозиторію — вірити репозиторію
  і оновити CLAUDE.md.

## Підтримка цього файлу в актуальному стані

- Якщо в ході роботи зроблені зміни, що розходяться з цим файлом
  (нова палітра, нові шрифти, зміна структури тек, нові критичні файли) —
  ОНОВИТИ CLAUDE.md у тій самій сесії. Застарілий CLAUDE.md гірший за відсутній.

## Фініш сесії (обов'язково перед завершенням)

1. Перевірити, чи все зроблене в сесії відображено в CLAUDE.md — оновити, якщо ні.
2. Оновити відповідні файли в `/context`, якщо змінився контекст бренду чи проєкту.
3. Оновити `docs/план.md` — перенести зроблене, додати нове.
4. Закомітити всі зміни з осмисленим повідомленням.
5. Запушити в main.
6. Коротко підсумувати користувачу: що зроблено, що запушено, що лишилось на наступну сесію.

## Правила комунікації з користувачем

- Уся комунікація — **українською**: пояснення, звіти про зроблене, плани, питання,
  підсумки сесії, описи змін. Простими словами, без жаргону.
  Англійською лишаються тільки команди, шляхи, назви файлів, імена змінних і коміт-меседжі.
- Команди для терміналу давати готовим текстом для копіювання, з поясненням, що вони роблять.
- Не кидати кілька завдань одразу — по одному кроку за раз.
- Якщо щось піде не так — спочатку сказати, чи все ціле, потім розбиратись.
- Не припускати, що користувач пам'ятає попередні сесії — коротко нагадувати контекст.

## Як влаштована робота над проєктом

- Дмитро працює у зв'язці двох Клодів. У браузері (claude.ai, проєкт ReLink) відбувається
  обговорення, стратегія і підготовка ТЗ. Тут, у Claude Code — виробництво: файли, верстка,
  документи, правки сайту.
- Прямого зв'язку між двома Клодами немає. Готове ТЗ переносить Дмитро копіюванням.
  Тому ТЗ приходять у строгому форматі — це не примха, а формат передачі.
- Спільна точка правди — цей репозиторій. Тека `/context` синхронізується в knowledge
  браузерного проєкту, тому браузерний Клод бачить те, що ми сюди кладемо. Решта репо
  доступна йому через GitHub-конектор за запитом.
- Практичний наслідок: усе, що має пам'ятатись між сесіями і бути видимим браузерному
  Клоду, кладеться текстовим файлом у `/context`. Не тримати важливий контекст лише
  в переписці.
- У проєкті також працюватиме Надя (партнерка по ReLink) — вона читає той самий
  репозиторій зі свого акаунта. Тому файли в `/context` пишуться зрозуміло для людини,
  а не тільки для моделі.

## Правила роботи з задачами

- ТЗ приходить за шаблоном: (1) що на вході; (2) що зробити — нумерований список;
  (3) чого не робити; (4) що на виході.
- Якщо після показу результату користувач каже «не те» — НЕ робити наступну правку наосліп:
  спитати, що саме не так, зібрати повний список зауважень і переробити ОДИН раз.
- Нічого не комітити і не пушити без явного підтвердження користувача.
- Для PDF/DOCX: завжди рендерити прев'ю (наприклад, сторінки в PNG) і показувати
  ПЕРШ ніж вважати готовим. Верстку наосліп не здавати.
